# Lawyers' keys stay in the browser; the server decrypts files only with a key the browser hands over

The vault is encrypted with libsodium (SPEC.md §10; design in docs/m5-encryption-design.md). Each lawyer has a personal key pair made in their browser; the server stores its private key only encrypted under a key passphrase, generated in the browser and separate from the login password, and under a recovery key the lawyer keeps on paper. All lawyers share one group key pair, handed to each of them as a key grant: a lawyer's browser seals the group private key to the newcomer's public key, after the admin and that lawyer have each compared the newcomer's safety number with them. Ingest seals each item's random data key to the group public key, so the server can encrypt without being able to decrypt. Texts are decrypted in the browser. For a file, the browser opens its data key and hands it to the server for that clip only, in a cookie, and the server decrypts while it streams. A revocation is followed by a rotation: a new group key, and every data key resealed to it by a lawyer's browser, kept alongside the old ones until two other lawyers drawn at random have each passed a check of it. Code holders, who have no keys, get a key pair derived from their upload code.

The server never holds a private key, so a seized or leaked server holds nothing readable without a lawyer's key passphrase, and someone watching the running server sees only what passes through it at the time. Moving decryption back to the server, letting the login password unlock the key, or letting lawyers choose their passphrase would each look like a simplification and quietly undo this, which is why it is recorded.

## Considered Options

- **One key held by the server** (from an environment variable): protects only disks and backups stored apart from the key; the operator, and anyone who seizes the running server, reads everything.
- **Lawyers' keys on the server, unlocked by the login password**: protects the vault at rest, but the server sees every password at login, so anyone watching it gets the keys and every clip with them.
- **Everything decrypted in the browser, files included**: nothing readable passes through the server after ingest, but saving a decrypted 2 GB download works properly only in Chrome and Edge, and playing a video needs a Service Worker answering range requests, which Safari handles badly; much more JavaScript, for a small gain over this option.
- **A separate application that holds the keys** (as SecureDrop does): the only option a compromised server cannot defeat by sending different JavaScript, but no preview in the browser, a second program to build and install for every lawyer. Left for later, if that threat becomes the main one.
- **Each data key sealed to every lawyer** instead of a group key: a new lawyer would need every existing key resealed for them; the group key needs one grant.
- **Grants made automatically by any lawyer's browser** to whatever key the server lists: someone able to write to the database could add a key of their own.
- **A passphrase the lawyer chooses**: a seized database allows guessing every lawyer's passphrase offline, and the weakest one gives the group key.
- **Rotation checked by no one, or by whoever logs in next**: one lawyer, or two working together, could reseal junk and leave the vault unreadable once the old sealed keys are deleted.

## Consequences

- Encryption protects against the server, not between lawyers: every lawyer's key opens every clip, and case scoping remains the server's check. It keeps contents secret from the server but does not prove who wrote them: anyone with the group public key can encrypt to it. The hash record remains the check on the evidence copy.
- The server that stores the ciphertext also sends the JavaScript that holds the keys, so a server running malicious code can steal them; ingest also sees every upload in plaintext. Someone able to write to the database could replace the group public key and have new uploads sealed to them. M5's promise is about what the server stores, and SPEC.md §1 and §3 say so.
- Lawyers need JavaScript, libsodium.js (sumo build) and a second secret, the generated key passphrase, to read the vault. Lawyer pages carry a Content Security Policy allowing `'wasm-unsafe-eval'`.
- A lawyer who loses both their key passphrase and their recovery key starts a key reset from their own account; the admin confirms the new key and another lawyer grants it. What was sealed only to the old key (case labels, later their messages) is lost. The admin cannot reset anyone's key alone. If every lawyer lost their keys, the vault would be unreadable for good; uploads close while no lawyer holds the group key.
- The admin has no key and cannot read the vault, by construction.
- A rotation needs lawyers to log in: the server draws the rotator, the only one who reseals, and then two other lawyers whose browsers check the result; until both have passed, the old sealed keys remain. No role goes to whoever arrives first, so two lawyers acting together can never destroy the vault, and a reported failure counts only once a further lawyer, drawn outside both slots, confirms it. A lawyer who stalls, sits on a slot or disputes a check delays the rotation by a few days and is excluded from the rest of it. With fewer than three unsuspended lawyers holding a grant, a rotation cannot end.
- Grants and rotations trust the server's list of lawyer keys beyond the safety number checks; a signing key for the admin would remove that trust, at the cost of a key for the admin to keep and recover.
- Sealed boxes use X25519, which a future quantum computer could break. PyNaCl does not yet offer libsodium's post-quantum X-Wing; once it does, a new group key of that kind and a rotation reseal every data key without re-encrypting files. Copies taken before then stay exposed.

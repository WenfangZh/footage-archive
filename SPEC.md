# SPEC: footage archive for the defence (learning build)

Working title. This file is the source of truth for what we're building and why. If something here seems wrong or ambiguous, ask before guessing; decisions we change get written back here. Terms are defined in GLOSSARY.md; decisions that are hard to reverse are recorded in `docs/adr/`.

## 1. Purpose

A place to upload short phone videos of arrests and police operations at protests, so that defence lawyers can find footage relevant to their clients (mainly minors who are innocent or falsely accused) and check it against police reports (procès-verbaux).

Two principles shape everything:

- **Purpose limitation.** Footage is available only to verified defence lawyers, and only for a specific case. The archive is not a general pool of evidence.
- **Privacy by design.** The people most at risk are those who filmed and those in frame, mostly minors. We collect as little as possible, strip what identifies filmers, and aim for a server that holds no footage it can read: only lawyers' keys open what it stores, though it must handle each clip in the clear while preparing it (§9, ADR 0007).

## 2. Status

- Learning build: no real footage, no real users, nothing deployed beyond a local machine.
- Public GitHub repository, for visibility: everything committed is public and permanent, and the README says plainly that this is a learning build.
- Test data: our own recordings plus synthetic videos generated with ffmpeg.
- We still design for real stakes, since retrofitting security is far harder than building it in. Before any real use: external security review, legal review, and a partner organisation.

## 3. Threat model

| Threat | What's at risk | Main defence |
|---|---|---|
| Breach, seizure or compelled disclosure of the server | Everything stored | Data minimisation; the vault is encrypted to lawyers' keys, which the server holds only encrypted under each lawyer's generated key passphrase (M5, ADR 0007); full-disk encryption or memory-only quarantine, since deleted files can survive on disk (§12 Later) |
| A server running malicious code | Clips uploaded while it runs; lawyers' keys, through the JavaScript it sends | None from encryption: ingest must read each upload, and a web page runs the code its server sends (a known limit, ADR 0007); quarantine kept short-lived (§8, §9) |
| People trying to identify filmers or protesters | Identities, home locations | Metadata stripping, no accounts or codes linking clips, no public views |
| Lawyers acting for other parties | Footage used outside its purpose; exculpatory clips hidden or discredited | Admission by vouching, case-scoped search, count-based reports and tag removal (no single lawyer can hide a clip or a tag) |
| Phished or compromised lawyer account | Bulk access | Mandatory 2FA, case scoping with size caps, audit log, alerts |
| Malicious uploads | Lawyers' machines, archive credibility | Validation, quarantine, never executed, size caps, rate limits |
| Seizure of a code holder's phone or code card | The clip, its messages, the code holder's identity | Code card label never stored on the server, lawyers anonymous to code holders by default, lawyer tags never shown to code holders |
| Pressure on the admin | Anything the admin can see or do | Admin manages accounts, not content; acts on reports only by count; the admin's actions on accounts go to the audit log, where the lawyers concerned can read them |

Known limit outside our control: once a lawyer files a clip in a case, every party to that case can see it.

Known residual risk: cases (time window and area) and the audit log must be server-readable for matching and alerts, so a breach or seizure of the server reveals which lawyer looked into which incident and which clips they downloaded, in effect part of the defence's strategy. The case-area map's requests for map data show the server roughly where a lawyer is looking (not for which case), so the archive never logs them (ADR 0006). M5 encrypts the vault and case labels but not these, which matching, alerts and the admin's reading of the log need (docs/m5-encryption-design.md §8): a seized server shows which lawyer looked into which incident and which clips they opened, but not what any clip shows.

## 4. Non-goals

- No public views of footage: no gallery, feed, share links or embeds. Ever.
- No automated identification of people (no face recognition). The one exception: identifiers that can only belong to police or other public officials acting as such, like an officer's RIO number or a police armband, may be read automatically, for lawyers only. Anything a civilian could also carry or wear (a name tag, a face, clothing, a vehicle plate) is never identified automatically.
- No custom cryptography, password hashing or authentication.
- No social features.
- No real footage or real users during the learning build.

## 5. Roles

**Uploader, then code holder.** No account. The **uploader** uploads one video with optional fields and receives an upload code, shown once; one code covers exactly one clip. From then on the system knows only a **code holder**: whoever presents the code. That may be several people, or someone other than the filmer, and the system cannot tell them apart; messages from lawyers are written with that in mind. With the code they can come back to edit fields, delete the clip (its hash record is kept), and read or answer messages from lawyers. The fields as given at upload are kept as the **as-uploaded** values for stated time, stated location and tags; each later **edit** records which field changed and when. Old values of context and contact details are never kept. A stated location can be made vaguer from what is kept; a more precise one needs a new position. Codes are 28 random characters in Crockford's base32 (140 bits), shown in 7 groups of 4; case, dashes and look-alike letters are forgiven when typed. They are stored only as a keyed hash (HMAC-SHA-256 with a server secret), so they can be looked up without being stored. A code also gives its clip's code holder key, whose public half is stored on the clip (ADR 0001). The code travels only in form submissions, never in a URL, a cookie or a server session, so the server never sees two clips opened from one browser. Failed code attempts are rate-limited: after too many wrong codes from one connection, no code is checked, not even a right one, until the window ends. A lost code cannot be recovered.

**Defence lawyer.** Invitation only: the admin sends the **invitation** by email to the person's own professional address, and its link works once and expires (default 3 days, configurable). Admission requires:
1. verification that the person is a practising lawyer registered with a French bar, using the bar directory and confirming through the directory's contact details, never those supplied by the applicant;
2. a vouch from a trusted defence organisation or an existing lawyer;
3. admin approval.

An invited person is an **applicant** until admitted. They log in with their email address; their account also records their name and their bar. While someone is an applicant, the admin can send them a new invitation link until they have set a password (it makes earlier links stop working), or decline them: a **declined applicant** cannot log in, and their name, bar and email address are erased, leaving the account only as an identifier for the audit log. Only an admitted, unsuspended **lawyer** can create cases or see anything about clips; a **suspended lawyer** sees nothing until reinstated. Throughout this spec, "lawyer" means the admitted, unsuspended kind. 2FA mandatory, set up as an applicant, before admission. So is a **personal key** (from M5, ADR 0007): the applicant makes it in their browser, protected by a **key passphrase** and a **recovery key**, both generated in the browser and shown once, and the admin compares its **safety number** with them through the bar directory's contact details before admitting them. An admitted lawyer reads the vault only once another lawyer, after comparing the same safety number with them directly, has given them a **key grant** of the **group key**. Access is case-scoped (§7). Admin can suspend a lawyer at any time; suspension removes access at once (including any role in a running rotation of the group key) and nothing else, and **reinstatement** undoes it. Admin can also **revoke** a lawyer, after an explicit confirmation step: revocation closes all their cases and can never be undone. Neither suspension nor revocation deletes anything the lawyer did: their audit entries stay, messages they sent stay visible to code holders (marked "this lawyer no longer has access"), and clips are unaffected; revocation removes only the account's means of logging in (password, second factor, sessions) and its key grants, after which the group key is renewed (a **rotation**) by a lawyer drawn at random, and the old one deleted once two other lawyers, also drawn at random, have each passed a check of the new one. A revoked lawyer's or declined applicant's email address no longer logs in and can be invited again; that makes a new applicant, who needs verification, a vouch and admission like anyone else, while the old account stays as it was. A revoked lawyer's address is kept, though not for logging in, so that the admin is warned before inviting it again. In the learning build, steps 1 and 2 are recorded as fields on the account (`verified_via`, `vouched_by`), not integrated with anything external.

**Admin.** Manages invitations, admissions, declining applicants, suspensions, reinstatements and revocations; approves cases larger than the caps (§7); deletes withdrawn clips (§7) and nothing else; receives **alerts** (unusual lawyer activity, §7, many failed logins for one account, §10, a backed-up ingest queue, §9, and from M5 a rejected rotation, a disputed rotation check, a rotator, checker or confirmer who ran out of time, a rotation attempt given up because no one could be drawn, fewer than three lawyers eligible for a rotation for 7 days, and a key grant that fails its recipient's check) on the admin's pages in the archive, not by email for now; can read the whole audit log and each clip's tag history. 2FA mandatory. Holds no key, so cannot read footage or vault contents (from M5).

Optional uploader accounts (from the first draft) are deferred: see §13.

## 6. Data: index vs vault

The server can only filter on what it can read, so filterable fields live in a search index restricted to data that is harmless if exposed. Everything else lives in the vault.

- **Index (server-readable):** capture time (precise; both the metadata time and the stated time, see §8), location (the stated location as a set of the grid's finest cells, ADR 0009, and the metadata location as one cell sized by a precision the uploader chooses, ADR 0004; the grid is H3, its finest cells are resolution 11, about 50 m across, and that limit is a setting that can be made coarser but never finer, ADR 0003), duration, resolution, tags (with their source, removal proposals and whether lawyers have removed them), as-uploaded values and edit records, upload time, clip status (processing, ready, failed, withdrawn), reports (from which the content warning and doubt marker follow), which lawyer exchanged messages about which clip (each message's direction, kind and whether its lawyer chose to be named, but not its text), lawyers' settings, hash record. Upload time, edit times, message times and the hash record's times are stored only to their 4-hour block (00h–04h, 04h–08h and so on, Paris time): an exact time could be matched against connection logs to find the uploader, and hashing runs minutes after upload.
- **Vault (encrypted from M5, ADR 0007, ADR 0008):** evidence copy, proxy, free-text context, any contact details the uploader or code holder chose to give, message texts. Only lawyers' keys open it; a code holder's own texts also open with their upload code, and a message only with the clip's upload code or the personal key of the lawyer in its thread (never the group key, so another lawyer or a rotation never reaches it). Case labels are encrypted too, to their lawyer's own key. No location is stored at better than grid precision, anywhere: precise GPS shows where the filmer stood, which for a clip filmed from a window is their home.

Until M5 is built the vault is plaintext, but all vault access goes through a single storage interface so that encryption can be added without touching callers.

## 7. Lawyer access (case-scoped)

- A lawyer creates a case: a **case label** (no client names), plus a time window and area taken from the police report. A case belongs to exactly one lawyer and covers one incident: it is a search scope, not the legal proceeding. Co-counsel each create their own case; a client arrested twice means two cases. Each case also has a **margin** around its time window and area, fixed when it is created (by default 10 minutes and one ring of the grid's finest cells; each lawyer sets their own defaults). The area is a set of the grid's finest cells, made from a place and a radius (or, from M4.5, picked on a map); from M9 the place can be looked up by address (ADR 0011); the coordinates typed to make it are not kept, and the case does not store the map's view. A case's time window is at most 2 hours and its area at most 2 km across (its two farthest points, edge to edge), margin included (both configurable, but never higher than the **ceiling**); a larger case needs admin approval, and the request is logged. The lawyer gives a **lawyer's reason** with the request (never a client's name); the admin sees the case's time window and area and that reason, not its case label, and approves or refuses it, optionally with a note of their own, which the lawyer sees and which is kept. The reason is deleted once the admin decides, or once the case is closed first. Until it is approved, the case cannot be used; a refused case is closed. No case goes beyond the ceiling of 24 hours and 10 km across, margin included, even with approval: it is fixed in the code, so raising it takes a public change. The window and area are fixed once created: to change them, the lawyer creates a new case. A lawyer can close a case; a closed case allows no searches, previews or downloads, but stays in the audit log. Cases close automatically after a period without use (default 1 year, configurable): a search, preview or download is a use, and the period starts when the case is created; the last use is read from the audit log. Every closing, whoever or whatever causes it (the lawyer, revocation, the admin's refusal, no use), writes an audit entry naming the case's lawyer. A case's page shows its own audit entries, and the lawyer's closed cases stay listed apart.
- Search returns only clips that match the case: any part of the clip (stated time to stated time plus duration) overlaps the time window, and any cell of its stated location overlaps the area, each widened by the case's **margin**. Results come in two groups: **core matches**, inside the time window and area themselves, then **margin matches**, found only in the margin. There is no global browsing.
- Lawyers watch low-res proxies and can download the evidence copy with its hash record. Alongside each clip they see its metadata time and location, its stated location as a number of cells, a size and the centre of the cell nearest its middle (never an averaged point, which could read as finer than the grid), its as-uploaded values, its edits, its context, and any contact details the code holder chose to leave; a stated time that differs from the metadata time by more than a threshold (default 15 minutes, configurable) is highlighted. A clip is reached only through one of the lawyer's own usable cases that it matches. The one exception is the lawyer's messages page (below), which shows their own threads, each with its clip's identifier only: no clip page, preview, download or other detail of the clip. Each view of a clip's page and each preview is logged, except that the same clip viewed or watched again in the same case within 2 hours is not logged again (a video player fetches one file in many pieces). Every download of an evidence copy is logged; a download resumed within 2 hours is the same one, but any request starting from the file's first byte is logged anew. Its hash record downloads as a JSON file.
- Lawyers' actions go to an append-only audit log: case creation and closing, request for a larger case, search, viewing a clip's page, preview, download, sending a message or a reply, tag addition, tag removal or restoration proposal and its cancellation, the removal or restoration that a third open proposal causes, report and its cancellation, the withdrawal that a second report causes, and from M5 key grants, key resets and rotations with their checks. Each entry records lawyer, case, action, time, and the clip where there is one (for searches, the numbers of core and margin matches instead; a reply names no case, since it is sent from the messages page). The admin's actions on applicants' and lawyers' accounts (each invitation link sent, admission, declining, suspension, reinstatement and revocation) go to the same log, each entry recording the admin, the person concerned, the action and the time; so do the admin's approval or refusal of a larger case, which also record the case, the admin's deletion of a withdrawn clip, which records the clip, and the admin's temporary raise of one lawyer's alert limit, which records the limit before and after and for how many days. When the archive starts with size caps or alert limits different from the last ones recorded, an entry records the numbers before and after; it names no one, since the server's configuration changed them. Entries are kept compact (keys and identifiers rather than text). Requests for the map's data are not lawyer actions in this sense, and are never logged (ADR 0006). The admin can read the whole log; each lawyer can read their own entries, including the admin's actions on their account; no one else can read any of it.
- Lawyers can add tags to a clip they can see, default or custom, and propose removing any tag, including the code holder's. A custom tag is shown to every lawyer whose case matches the clip, so its form warns the lawyer to write nothing about their own case. A tag the clip already shows, or one lawyers have removed, cannot be added again: the same default tag, or a custom tag with the same text ignoring case and surrounding spaces (a custom tag named like a default tag, in French or English, counts as that default tag). A tag is removed once three different lawyers, each through a usable case of their own that matches the clip, have proposed removing it, and a removed tag comes back only by the same rule (three proposals to restore it); lawyers see removed tags in a list of their own, apart from the clip's tags, where they can propose restoring them. A lawyer has at most one open proposal per tag, and can cancel it; a removal or restoration closes the proposals that made it, so counting starts again. Removal applies to what lawyers see: the code holder's own view and the as-uploaded values are untouched, and the code holder's later edits keep a removed tag removed. But a tag the code holder deletes takes its removal and its open proposals with it: added again later, by the code holder in an edit or by a lawyer, it is a new tag, counted from zero, which lawyers see until they remove it again. Deleting a tag and adding it back, spelt the same, in one edit changes nothing. The audit log names a tag by its identifier, never by its text.
- Lawyers see each tag's source (code holder or lawyer, never which lawyer), shown by colour plus a short word ("code holder", "lawyer") so it does not rely on colour alone. Colours are configurable; defaults are blue for the code holder and orange, a pair that stays distinct for colour-blind readers. Lawyer tags and removal proposals are never shown to the code holder.
- The admin can view each clip's **tag history**: every tag lawyers added, proposed for removal or restoration (and cancelled proposals), removed and restored on that clip, by whom and when, and from the clip's edits, when the code holder changed their tags (the values are not kept, so a tag the code holder has since deleted shows without its name), to spot disputes over a clip's tags. It is drawn from the audit log and the clip's edits, not kept separately. The admin's list of clips with disputed tags (those on which a lawyer has ever proposed removing or restoring a tag, even if the proposal was cancelled, the dispute settled or the clip deleted) shows clips by identifier only. No lawyer sees the tag history.
- Unusual volume raises an alert to the admin: by default 20 downloads by one lawyer within an hour, or 5 cases created within 24 hours (all configurable), counted from the audit log. The admin can raise one lawyer's limit for at most 3 days (configurable), for example during a large case; each raise is logged with the limit before and after.
- A lawyer can report a clip, through a usable case of their own that matches it. A report that the time or place is wrong reaches the code holder as a message in that lawyer's thread, with an optional note, which the code holder can answer. A doubt about authenticity gets no verdict from anyone: other lawyers whose cases match the clip see a neutral **doubt marker** ("a lawyer has raised a doubt about this clip"), with no free text, which could leak one lawyer's case to another. A report of inappropriate content (not protest footage, sexual content, footage posted to expose someone) cannot be judged by the admin, who cannot view clips, so it works by count: one report puts a **content warning** on the clip for other lawyers (the preview stays behind a "show anyway" step); a report from a second, different lawyer **withdraws** the clip: it disappears from every search, clip page, preview and download, and the code holder sees on their page that it was withdrawn. The code holder is not told of a doubt or of a first report of inappropriate content. The admin sees a list of withdrawn clips, by identifier, and may delete one; its hash record is kept. A withdrawn clip has no way back (§13), and revoking a reporter does not undo it. No single lawyer can hide a clip. A lawyer can cancel their own doubt, and their own report of inappropriate content while the clip is not withdrawn; a report of wrong time or place cannot be cancelled, since the code holder has it already (a correction is another message).
- A lawyer can send a message to the code holder of a clip, through a usable case of their own that matches it. The messages between one lawyer and the code holder of one clip form a **thread**. By default the code holder sees the sender only as "a verified defence lawyer"; each lawyer has a setting to identify themselves (name and bar) by default, and can override it per message. The code holder sees messages on their next visit, those not yet shown to them marked as new (a mark stored with the message, which no lawyer can see), with each of the clip's lawyers told apart as lawyer A, B and so on, and decides whether to reply or identify themselves; lawyers are never told whether or when the code holder read a message. A lawyer reads and answers their threads on their own messages page, which needs no open case, so closing a case does not cut a code holder's answer off; reading is not logged. A code holder cannot reply to a lawyer who is suspended or revoked, or who holds no personal key. A lawyer who replaces their key after an exposure report keeps their messages, which their browser moves to the new key as it does case labels; after a key reset, the lawyer can no longer read the messages sealed to their old key, while the code holder still can. Threads, reports and tag proposals go with their clip when it is deleted (the audit entries stay); a withdrawn clip's threads can still be read and answered on both sides until they expire or the clip is deleted. Messages are deleted a set time after the last message in their thread (default 6 months, configurable), counted from the end of that message's 4-hour block, so that no message is deleted early; each thread shows when, and lawyers are warned to save what they need into their own records. A lawyer keeps their letter (lawyer A, B and so on) on the clip after their thread is deleted, so that no letter ever passes to another lawyer: what stays is that letter and which lawyer wrote about which clip, which the audit log holds anyway.
- A lawyer can choose to get an email **notification** when a code holder's message is waiting for them (on by default). It is one fixed text in French and English, "something is waiting for you in the archive", with a link to log in: it names no clip, sender, count or kind. One email goes out when something new starts waiting, and no other until the lawyer opens their messages; emails are sent at the end of each 4-hour block (§6), so the mail provider learns no more precise time, and only if something is still unopened then. Each lawyer's settings page holds their default margin, their identification setting and their notifications.

## 8. Upload

The interface is in French by default, with a visible switch to English (Django's built-in translation framework; see §11). A visitor whose browser prefers English gets English until they use the switch; a choice made with the switch always wins.

Upload happens in two steps. First the uploader sends the file; it goes straight to quarantine, and a quick ffprobe read there checks that it is a real video (if not, it is deleted at once and no code is issued) and extracts only the metadata time and GPS to pre-fill the form (nothing is executed or served). Only the container formats phones record in are accepted (MP4/QuickTime, Matroska/WebM). A metadata time without a UTC offset, or a placeholder time (1904 or 1970), counts as no metadata time. Then the uploader fills in and confirms the fields below, and only then is the upload code issued. The full ingest (§9) runs after that. If the form is not confirmed within a set time (default 2 hours, configurable), the original is deleted and nothing is kept, not even a hash, since no clip ever existed.

With JavaScript, the browser sends the file in pieces (the tus protocol, from M6.3), so an upload cut off by a lost connection or a reloaded page resumes where it stopped instead of starting over. Until its last piece arrives it is a **partial upload**: it waits in quarantine like an original, is never served, and keeps nothing sent with it (not even the file name); its address is random, and whoever holds it can continue or abandon the upload, so the archive never writes it to its logs (and a deployment's web server must not either); one that is not finished within a set time after it started (default 2 hours, configurable) is deleted. Starting a partial upload counts towards the rate limit below and is refused while uploads are closed. Once it is complete, the quick read runs as above, and the form's own time limit starts then. The uploader's browser keeps where the upload can resume: its address and creation time, and the file's size, type and date, never its name. It forgets them once the form is reached, or, for an upload that was abandoned, when the upload page is next opened after the partial upload's time limit. Without JavaScript (for example in Tor Browser's safest mode), the file is sent in one piece as before.

Everything is optional except the video:

- capture time: the **metadata time** is read from the file and can never be changed by anyone; it is unreliable (phone clocks, time zones, re-saving apps) and trivial to forge, which is why it is kept as found. The uploader sees it and gives a **stated time**, pre-filled with the metadata time, which they may keep or replace. Lawyers see both;
- location: a **stated location**, the grid's finest cells (about 50 m) that cover where it was filmed (ADR 0009): painted on a map (from M6.6) or given as coordinates plus a precision (exact spot, street or neighbourhood), which stand for the finest cells of a hexagon about 50, 130 or 340 m across (about the same area: the small cells' outline is jagged). From M9, a street can be looked up by name to find the place on the map, or, without JavaScript, to fill the coordinates (ADR 0011). When the file has GPS, its cell is painted to begin with (or, without JavaScript, the coordinates are pre-filled as an exact spot). If both cells and coordinates are sent, the coordinates win. A stated location is at most 1 km across, measured as a case's area is (its two farthest points, edge to edge): the stated location's ceiling, fixed in the code, with no approval route. When the file has GPS, the uploader also chooses how precisely its position is kept as the **metadata location**: a cell of about 50 m (pre-selected), 130 m or 340 m. The code holder can later make it coarser, never finer (ADR 0004);
- tags: defaults below, plus custom tags;
- context: free text;
- contact details or social media handle: explicit opt-in, behind a plain-language warning that lawyers whose case finds the clip will see them, and that anyone else who obtains this information could use it against them.

If the stated time or stated location is left empty, the form warns plainly that no lawyer will be able to find the clip until both are given (see §13 on how long such clips are kept).

The map (from M6.5) is the one lawyers use for case areas (ADR 0006), made first for phones, since uploaders and code holders mostly use one (from M6.6). Its gestures are the usual ones: one finger moves the map; pinching, a double tap or the scroll wheel zooms. Once zoomed in far enough for a cell to take a fingertip, a faint grid of the 50 m cells appears, and a tap adds or removes one cell; on a computer, dragging with Shift held down adds every cell it crosses, as for lawyers. The map shows the place's size against the stated location's ceiling. Only the cells' ids leave the page, as for case areas: nothing else of it (a tap's position, the map's view or zoom) is kept or logged, and typed coordinates are the only way a position reaches the server. The code holder's edit page shows the cells kept, which can be added to or removed freely; removing them all clears the stated location, and the warning about an empty one applies. The map is on the form and on the edit page, and loads only when asked for. Everything it loads comes from the archive. Its data is served to an uploader or code holder only with a **map pass**, which the form hands out for an unconfirmed original and the edit page for a valid upload code, each time either is shown: a signed time stamp that names no upload, valid for as long as an unconfirmed original is kept (2 hours by default) from when the page was shown. The pass travels in the path of the map data's routes, which are never logged, by the archive or (a deployment's duty) its web server. When a pass has expired, the map says so, and coordinates still work. Outside the map's extract (Île-de-France for now) the map is blank; without JavaScript or WebGL2, coordinates still work, and on the edit page, coordinates given replace the cells, while empty ones keep them; a box there removes the place, which needs no JavaScript.

Tags are stored as stable, language-neutral keys and shown by their **tag name** in the user's language (French and English for now). Default tags describe what can be seen, not conclusions, and their keys stay country-neutral so the list can travel; the French tag names use the French terms.

| Key | English | French |
|---|---|---|
| `arrest` | Arrest | Interpellation |
| `use_of_force` | Use of force | Recours à la force |
| `officer_id_legible` | Officer ID number legible | RIO lisible |
| `officer_id_not_visible` | Officer ID number not visible | RIO non visible |
| `police_armband_visible` | Police armband visible | Brassard police visible |
| `no_police_armband_visible` | No police armband visible | Pas de brassard police visible |

Custom tags are stored as typed, without translation.

After upload, show the upload code once on a **code card** designed to be screenshotted, with a clear "save this now, it cannot be recovered" message. The card shows the code and a **card label** the uploader types, pre-filled with a suggestion they can edit (e.g. built from the stated date and tags). The card label appears only on the card and is never stored on the server. A plain-language warning says that anyone who finds the card can read the clip's messages and delete it. The code can also be copied (M8.5), with a warning that copied text may reach other devices or apps.

Limits: cap by file size, not duration (default 2 GB, configurable). A file over the cap is refused whole, never cut: the form states the cap, the browser checks the file's size before sending it, and the server enforces it on the size a partial upload declares and on the bytes it receives, storing nothing beyond the cap. Rate-limit uploads; IPs may be used transiently for this (in cache, short TTL) but are never written to the database or logs. Limits are per connection and generous, since many phones at a protest can share one IP address (defaults: 20 uploads and 20 wrong codes per hour).

## 9. Ingest pipeline (background job)

1. The original is already in quarantine (§8), an area that is never served over the web.
2. Validate again with ffprobe, fully, that it is a real video (the first check ran at upload, §8); reject it otherwise.
3. Compute SHA-256 of the file exactly as received.
4. Compute per-stream hashes of the encoded packets (ffmpeg stream copy, no decoding).
5. Extract metadata (ffprobe; exiftool optional), confirming the quick read made at upload (§8). The metadata time goes to the index as found. GPS goes to the index as the metadata location, snapped to a cell of the size chosen at upload (§8); the precise value is never stored. Device make and model, software versions and unique identifiers are discarded.
6. Remux: copy the encoded video and audio streams into a new container of the same family (QuickTime or MP4 stays QuickTime or MP4, Matroska or WebM becomes Matroska) without decoding or re-encoding them, keeping only those streams (data tracks and cover art are dropped) and none of the container or stream metadata. This is the **evidence copy**. It is never re-encoded. Information the player needs that lives inside the streams (such as rotation) survives; times, locations and tags are held on the clip (§6), not in the file.
7. Recompute per-stream hashes on the evidence copy. They must equal step 4, or the job fails loudly.
8. Generate a low-res H.264 proxy for previews. The proxy is never evidence.
9. Delete the original: once step 7 passes, it is the only copy still carrying identifying metadata. Keep the hash record (results of steps 3, 4 and 7, plus the SHA-256 of the evidence copy so a lawyer can check a download, with timestamps kept to their 4-hour block, §6). It proves the frames are untouched, and lets a copy of the original (for example, still on the filmer's phone) be matched against what we hold.

If a job fails or exceeds its time limit (default 10 minutes per attempt, configurable), it is retried with backoff: five retries, after 1, 2, 4, 8 and 16 minutes. A file that is not a video, or no longer shows what the quick read at upload found, fails at once without retries. After the last failure, the original is deleted immediately, along with the clip's context and contact details, and the clip shows a failed status, so a code holder who returns with their code knows to upload again (with a new code). Clips still waiting for ingest are never deleted for age; a backed-up queue alerts the admin instead.

Later: a trusted timestamp (RFC 3161) over the hash record.

The queue counts as backed up when more than 20 clips are waiting, or when a clip is still waiting 2 hours after the end of its upload time's 4-hour block (both configurable): with all its retries, ingest takes at most about 1.5 hours, and the check needs no time more precise than the one stored (§6); the alert's own time is kept only to its 4-hour block too. The alert is shown once until the admin has seen it.

## 10. Security requirements

- Django's auth with the Argon2 password hasher. No hand-written auth or crypto.
- Encryption only through libsodium: PyNaCl on the server, libsodium.js in lawyers' browsers. M5 starts with a written design that is reviewed before any code is written. It must cover key management (how a newly admitted lawyer gets access to existing clips, revocation, recovery); how code holders, who have no keys, can still read messages addressed to them and their own context and contact details; whether case labels, case areas and audit details can be encrypted without breaking matching and alerts (§3); and whether lawyers' two-factor keys and recovery codes, readable in the database today, should be encrypted. The design (docs/m5-encryption-design.md, ADR 0007, ADR 0008) answers: lawyers' private keys never reach the server unencrypted, a group key gives every lawyer access, a new lawyer receives it from another lawyer after both the admin and that lawyer checked their key, a revocation renews it, and recovery is a recovery key, or a new key the lawyer starts from their own account, confirmed by the admin and granted by a lawyer; code holders get a key derived from their upload code; case labels are encrypted, while case areas, time windows and the audit log stay readable for matching and alerts; two-factor secrets are not encrypted in M5.
- 2FA for applicants, lawyers and the admin through django-otp (ADR 0005): codes from an authenticator app, and ten single-use recovery codes shown once at setup. No SMS or email codes, and no page that turns it off. The QR code for setup is drawn on the server (segno). Wrong codes are slowed down by django-otp; many of them after a right password suggest a stolen password, and count towards the alert for many failed logins for one account.
- Failed logins are rate-limited per connection and per account on one connection (defaults: 20 and 10 per hour, configurable): over a limit, no password is checked, not even a right one, until the window ends. Limiting per account from anywhere would let anyone lock a lawyer out, so many failed logins or wrong second-factor codes for one account across connections (default 30 per hour) raise an alert to the admin instead. As with uploads, only keyed hashes of the IP address and the email address are kept, in the cache.
- A login lasts at most 24 hours (configurable).
- Django's built-in admin site is not installed: it can show and change any database table, which conflicts with an admin who manages accounts, not content (§5). The admin works only through the archive's own pages, each allowing one action.
- Uploaded files are untrusted: validate them, never execute them, never serve them from quarantine. Only video is accepted.
- No IP addresses, user agents or fields supplied by uploaders or code holders in application logs. (The audit log is not an application log; its entries hold keys and identifiers, not such text.)
- The audit log is append-only: the application has no update or delete path for it.
- Secrets come from environment variables; `.env` is gitignored.

## 11. Stack

- Python 3.12 in a pyenv virtualenv (`footage-archive`, selected via `.python-version`), Django, server-rendered templates, minimal JavaScript. The map (M4.5 for case areas, M6.5 for the stated location) needs more JavaScript than the rest: MapLibre GL JS, pmtiles and h3-js, copied into the repository with no package manager or build step. The map's style and fonts are generated once, on a developer's machine, from @protomaps/basemaps (with Node) and Protomaps' Noto Sans glyphs; neither is a dependency of the archive. The typed place and radius keep working without it. Reading the vault (M5) needs libsodium.js (sumo build) in the browser, and resumable uploads (M6.3) need tus-js-client, both copied into the repository in the same way. The server side of the tus protocol is the archive's own code. Function over looks.
- Django's built-in translation framework (its tools need GNU gettext, from apt): French by default, English available. Every user-facing string is translatable from day one.
- SQLite in development, Postgres later.
- ffmpeg and ffprobe from apt. Whether package installs (apt and pip) are done by hand or by the agent is set per machine, in that machine's Claude Code instructions (`~/.claude/CLAUDE.machine.md`).
- Background tasks with Huey, its queue in a SQLite file of its own: no broker to run, retries with backoff and scheduled tasks built in. Tasks carry only identifiers. The worker runs as `python manage.py run_huey`.
- Email through Django's email framework: in development each email is printed in the terminal of the process that sends it, and nothing is sent; a mail provider, reached through Django's SMTP backend and configured from environment variables, comes with deployment. Emails (invitations now, notifications from M6.2) never carry footage, anything about a clip, or vault contents.
- File storage behind Django's storage API: local disk now, S3-compatible object storage later.
- pytest with pytest-django. Test videos are generated with ffmpeg (synthetic `lavfi` sources with injected fake GPS and device tags), so tests never need real footage.
- Development on Ubuntu (WSL2 or a remote server) with pyenv, the repo in the Linux filesystem.

- in the dark theme, chosen or the system's, the case-area and stated-location maps load the dark style, and an expired map pass still says so with it; the painted cells' outline and the grid lines meet 3:1 contrast against the dark style's land, water and buildings at the zooms where cells are picked (a test reads both styles' colours and the cells' colours; checked by hand in both themes);
- and with `DJANGO_BEHIND_TLS_PROXY` on, a request the proxy marks as HTTPS counts as secure (the theme cookie gets `Secure`, the map style's addresses are `https://`), and with it off, the header is ignored.

**M8.7: A case's time window.** Asked for by the owner after using M8.5's typed times on a new case.
- The new case form opens with today's date (French time) in both the start's and the end's boxes, and no time.
- Beside each date's boxes, a calendar fills them (a static script; without it the boxes work alone). The upload and the code holder's page keep the boxes only, as M8.5 decided.
- Once the start is complete, the end fills in an hour later (into the next day if need be), until the lawyer gives an end of their own; an end sent back by a refused form is theirs too.
- Not changed: the upload's progress. Sent straight to the server, it rises steadily across the 20 MB pieces (M6.3); through an SSH port forward it stalls and jumps, because the browser counts what the tunnel's local end has accepted.
*Done when*:
- a new case form shows today's date in French time in both date boxes and no time (a test);
- and, checked by hand in Chromium and Firefox: the calendar fills the date boxes and shows a typed date; a complete start fills the end an hour later, also across midnight; and an end typed or picked by the lawyer is no longer replaced.

**M9: Looking up a place by name.** Few people know coordinates, and police reports give addresses (ADR 0011). The forms that take a place gain a search in the archive's own copy of the Base Adresse Nationale (Licence Ouverte 2.0) for Île-de-France, the area the map covers, downloaded by `python manage.py fetch_address_data` into the data folder, out of git, with its publication date.
- Uploaders and code holders search **streets**; lawyers creating a case search **addresses**, with house numbers. A street moves the map to it, where the person paints the cells as before; an address fills a case's place, whose radius the lawyer sets. Without JavaScript, a search step lists the matches and the chosen one fills the typed coordinates (a street gives its middle, with the precision "street"), which the person can still change; the rest of the form is kept.
- The search is SQLite's full-text search: it forgives accents, case and the usual abbreviations ("bd", "av.", "fg"), not typos, and lists places in Paris first. It returns at most 10 matches.
- What is typed goes to the server in the body of a request, on routes under the map data's prefixes: a map pass's for uploaders and code holders, a lawyer's for cases. It is never stored or logged; only the cells the forms already keep are kept. The routes are rate-limited per connection.
- Typed coordinates stay, folded away under "Type coordinates instead".
*Done when*:
- `fetch_address_data` builds the index from the BAN's files, and running it again gives the same index, or a newer one, without a half-built one ever in use;
- a search finds a street despite accents, case and abbreviations, lists Paris first, returns at most 10 matches, and a lawyer's search finds a house number while an uploader's finds streets only;
- the uploader's and code holder's search needs a valid map pass and the lawyer's a lawyer, as the map data does; the query appears in no log, audit entry or stored row, and the routes refuse a GET, an over-long query and too many searches from one connection;
- without JavaScript, the search step fills the coordinates and keeps the rest of the form, on the upload, the code holder's page and a new case;
- with JavaScript, choosing a street moves the map and choosing an address fills the case's place (checked by hand in Chromium and Firefox);
- and the licences page and THIRD_PARTY_NOTICES.md name the BAN, its licence and the data's date.

## 13. Open questions

- Keep optional uploader accounts at all, given that they link clips together? The same question covers letting a code holder attach a new clip to an existing upload code (for now: one code per clip, always). Linking has no collision risk, but it lets the server, and anyone who seizes it or the code, build a list of protests one person attended, and one leaked code then exposes every linked clip.
- Discard the untouched original after hashing (current default), or also keep it in the vault? Keeping it would keep precise GPS inside the file, which ADR 0002 rules out unless that decision is revisited.
- The hash record keeps the original's SHA-256 even after the clip is deleted, so that a copy of the original can be matched against what we held. The same match works against the filmer: if their phone and the server are both seized, it proves that the video on the phone was uploaded. For the legal review: is this worth keeping, and for how long after deletion?
- **Clips with no capture time or no location (important, revisit).** They can never match a case, so as they stand they are useless. We hold them for a while so the code holder can come back and add the missing time or place, but holding unfindable footage indefinitely conflicts with data minimisation. To decide: how long they are held, whether the code holder is warned, and what happens when the period ends.
- **Failed clips.** When ingest fails for good (§9), the original is deleted, and so are the context and contact details; no evidence copy, proxy or hash record was ever kept. The clip itself stays, with its times, locations, tags, as-uploaded values and edits, so that a code holder who comes back with the code learns that ingest failed and knows to upload again; with the code they can also delete what is left. As it stands, nothing else deletes it. To decide, alongside the question above: how long a failed clip is kept, and what happens when that period ends.
- Files over the size cap (§8): what can a filmer with a bigger video do? Trimming it on the phone often re-encodes it and rewrites its metadata time. Resumable uploads (M6.3) make a long upload survive a dropped connection, which a higher cap would need, though a partial upload is still deleted 2 hours after it starts.
- **Space and bandwidth taken by repeated uploads** (§8): the rate limit counts per connection, so one connection may start many partial uploads within it, and many connections (people behind one carrier's shared addresses, or an attacker with many addresses) many more, each up to the size cap and each held for 2 hours; an unconfirmed original is held as long. The form and the code holder's edit page also hand out a new map pass each time they are shown, so one upload, or one upload code, gives as many passes as it is opened, each of which lets its holder download the whole of the map's data (about 300 MB) until it expires. Should there be caps on the total size of partial uploads and unconfirmed originals in quarantine, and on the map data served to uploaders, and what should happen when one is reached?
- **Withdrawn clips have no way back** (§7): the admin can only delete one, and the reports behind it cannot be cancelled. Two lawyers acting together can therefore hide a clip for good, which collusion detection (§12, Later) would only reveal after the fact. Should anyone be able to restore a withdrawn clip, and on what grounds, given that no one but lawyers can view it?
- **Showing a clip's place on a map to lawyers** (§7): the clip page gives the stated location as a number of cells, a size and a centre. Drawing the cells on the lawyers' map would show its shape, for example a stretch of street; what would it take, and is it worth it?
- **Snapping to streets** (§8): a tap on a street could pick the cells along it, from the road shapes in the map's data. The data has no outlines of neighbourhoods, only their names.
- Error reports: they show no frame's variables (`core.error_reports`), since Django's own frames would otherwise show what a function declares sensitive; views also hide sensitive form fields, and Django hides cookies whose names contain "key". They still show the request's GET and POST data (but the fields a view hides), uploaded file names, headers (with the IP address, user agent and referer), the account's identifier and exception messages; all of these need a decision before anything sends reports. Nothing does today (no `ADMINS`, no error tracker).
- **Account recovery.** M3 handles neither a lost password nor a lost second factor (beyond recovery codes). Django's password reset by email is the usual answer for a password. For a second factor, a new invitation and help from the admin are both possible routes, but neither may let the admin take over a lawyer's account, and with it the lawyer's cases. M5 covers lawyers' keys (a recovery key, or a new key the lawyer starts themselves, confirmed by the admin and granted by a lawyer, docs/m5-encryption-design.md §5.6), and makes a taken-over account worth less: without the key passphrase, it opens nothing in the vault.
- **Applicants left waiting.** An applicant the admin neither admits nor declines stays an applicant indefinitely, with their name, bar and email address. Should applicants be declined automatically after a period, and how long?
- Long term: stay standalone, or move to (or build on) GlobaLeaks for international use? Language-neutral tag keys keep that door open.
- **Licence questions for the legal review** (M7, ADR 0010): whether serving the map's tiles to lawyers and uploaders is public use of a database under the ODbL, and whether that also obliges us to offer the extract itself (OpenStreetMap's own guidelines do not say whether vector tiles are a database or a produced work); whether code written largely with an AI assistant is protected by copyright, in France and elsewhere, which bounds how far any licence can be enforced; whether the licences' disclaimers of warranty and liability hold under French law; and who should hold the rights if an association runs the service.
- Before any real use: hosting-provider data retention rules versus anonymity, hosting-provider duties on illegal content (removal once aware, reporting e.g. to PHAROS) given that the admin cannot view clips, GDPR legal basis and impact assessment (AIPD), who operates the service (an association?), and which defence organisations could vouch for lawyers.
